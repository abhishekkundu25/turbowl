## Equality

### The clique scaling tests

`scaling_reasoner_same_as_clique` builds n aliases chained by `owl:sameAs`,
with 10 triples on each. At every size it checks the stored tuples
(10n + 3) and the expanded closure (11n² + 2) exactly. Time is the fastest
of 7 runs per size.

| n | time | time / n |
|---:|---:|---:|
| 256 | 57.5 µs | 224.7 ns |
| 512 | 111.0 µs | 216.8 ns |
| 1,024 | 224.8 µs | 219.5 ns |
| 2,048 | 521.9 µs | 254.9 ns |
| 4,096 | 1.034 ms | 252.6 ns |

The fitted exponent is 1.057 (the bound for linear is 1.25).

`scaling_reasoner_same_as_clique_expansion_per_triple` times `triples()`
on the same cliques, per output triple. The output has 11n² + 2 triples by
definition.

| n | output triples | time per triple |
|---:|---:|---:|
| 16 | 2,818 | 35.5 ns |
| 32 | 11,266 | 34.9 ns |
| 64 | 45,058 | 34.8 ns |
| 128 | 180,226 | 34.3 ns |
| 256 | 720,898 | 34.4 ns |

The fitted exponent is −0.011 (the bound for constant is 0.25). Both tests
ran alone ([`scaling-clique.txt`](data/2026-11-05-wave-4/scaling-clique.txt)).

### `sameas-clique`

This is the bench's equality scenario: `a0 owl:sameAs a1`, ...,
`a998 owl:sameAs a999`, and 10 triples on each alias, 10,999 input
triples. Once expanded, its closure holds 11,000,002 triples: 1,000,000
`owl:sameAs` triples, every alias's 10 triples on every alias
(10,000,000), and the two facts that `owl:Thing` and `owl:Nothing` are
classes. Each engine had 3 runs and the bench's 600 s timeout. The load
average was 2.73 before and 3.49 after.

```sh
cargo run --release -p turbowl-bench -- --only sameas-clique --runs 3
```

| Engine | Reasoning ms | Range | Load ms | Peak MiB | Closure |
|---|---:|---|---:|---:|---:|
| TurbOWL | 0.333 | 0.325–0.417 | 5.728 | 5.4 | 11,000,002 |
| `reasonable` | timeout (over 600 s) | | | | |
| Nemo | timeout (over 600 s) | | | | |

- TurbOWL stores 10,003 tuples: the aliases' 10,000 triples, rewritten to
  one representative, one `r owl:sameAs r`, and the two facts. It expands
  them only when they are read. The peak, 5.4 MiB (0.51 bytes per closure
  triple), is read before the bench's checks and includes the bench binary
  itself.
- TurbOWL's time does not include reading the expanded closure. At about
  35 ns per triple (the scaling test above), reading all 11 M takes about
  0.4 s. The bench read them all on every run and counted 11,000,002.
- `reasonable` and Nemo build the whole closure. Neither finished its
  first run within 600 s, and the bench stops an engine's runs after a
  timeout, so their memory is not known.

Raw results: [`bench-sameas-clique-7c31e93.json`](data/2026-11-05-wave-4/bench-sameas-clique-7c31e93.json)
and [`bench-sameas-clique-7c31e93.txt`](data/2026-11-05-wave-4/bench-sameas-clique-7c31e93.txt).

## Speed: this reasoner against wave 3 (a trend)

This reasoner ran alone on wave 3's scenarios, at `7c31e93` (the code of
`f8fc3b9`, clean tree), and is compared with wave 3's run at `3252f68`. The load average was 2.84 before and 3.32 after (wave 3's run:
6.69 and 8.64).

```sh
cargo run --release -p turbowl-bench -- --only brick-small1,brick-soda-hall,lubm-1,lubm-10,lubm-50,incremental-add,incremental-remove --engines turbowl --runs 3
cargo run --release -p turbowl-bench -- --compare docs/verification/data/2026-11-05-wave-3/bench-3252f68.json bench-trend-7c31e93.json
```

Reasoning time is the median of 3 runs, with the range in brackets. For
`incremental-*` it is the time per change.

| Scenario | Wave 3 ms | Wave 4 ms | Change | Wave 3 MiB | Wave 4 MiB | Closure |
|---|---:|---:|---:|---:|---:|---:|
| brick-small1 | 3.189 (3.145–3.270) | 4.424 (3.554–6.677) | +38.7% | 7.0 | 7.3 | 26,381 |
| brick-soda-hall | 6.896 (6.673–7.008) | 6.552 (6.546–6.574) | −5.0% | 8.6 | 8.4 | 57,652 |
| lubm-1 | 11.642 (11.600–12.022) | 11.164 (11.132–11.212) | −4.1% | 29.2 | 29.1 | 184,086 |
| lubm-10 | 143.263 (139.893–150.725) | 134.397 (134.258–134.562) | −6.2% | 283.3 | 283.2 | 2,024,317 |
| lubm-50 | 930.926 (812.554–1,015.339) | 738.760 (737.563–741.295) | −20.6% | 1,484.6 | 1,483.1 | 10,345,697 |
| incremental-add | 0.208 (0.203–0.217) | 0.203 (0.202–0.205) | −2.4% | 7.2 | 7.3 | 27,261 |
| incremental-remove | 2.946 (2.939–2.958) | 2.821 (2.817–2.830) | −4.2% | 13.7 | 13.8 | 25,620 |

The closures equal wave 3's in every scenario, and memory is the same.
Equality adds no cost that shows on these inputs: they have no
`owl:sameAs`, so nothing merges. The lower times are probably the lighter
load; one trend run cannot tell.

brick-small1 is the first scenario the bench runs, and its first runs came
while the machine warmed up. Ten more runs right after took 3.085 to
3.258 ms, median 3.123 ms, within wave 3's range
([`bench-brick-small1-10-7c31e93.txt`](data/2026-11-05-wave-4/bench-brick-small1-10-7c31e93.txt)).
