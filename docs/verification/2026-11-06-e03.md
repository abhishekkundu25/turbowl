# Verification: loop iteration 3, relations sized to their contents (2026-11-06)

The change: a relation gives back spare room above an eighth of its length
after a sort, a merge or a filter, merges grow by exactly what they add, and
an emptied recent part holds nothing (`eebb962`). The kept version before it
is `b1d4b93` (iteration 2); only records changed between the two. The
decision and the reasoning are iteration 3's row in `docs/specs/experiments.md`.

Raw results are in [`data/2026-11-06-e03/`](data/2026-11-06-e03/).

## Speed and memory

The bench at `b1d4b93` (before) and `eebb962` (after), TurbOWL alone, on one
thread, the editor-size scenarios, 5 runs each, interleaved twice. Medians.
The machine was busy, not quiet.

Load average (1 min) before each set: before 1: 2.46, before 2: 2.43, after 1: 2.15, after 2: 1.94.

Times are within the spread everywhere. On one thread the peak fell wherever
the store is large: lubm-50 by 43 MB, lubm-10 by 11, brick-buildings by 7. On
all cores nothing changed: that path already built exact vectors.

The store now holds 12.2 bytes per closure triple on one thread (21.2
before), but the peak fell by about half of the 93 MB the store gave back:
much of the spare capacity had never been touched, so it was never resident.
The implementer's probe, sampling the footprint every 200 µs, put the
one-thread peak at the very end of the run. What bounds it now: the held
state (39.6 bytes per closure triple), about 100 MB of memory freed during the
run that the allocator keeps, and 17 to 25 MB allocated after the last step.
