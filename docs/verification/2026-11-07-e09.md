# Verification: loop iteration 9, the dictionary's lookup table dropped during large parallel runs (2026-11-07)

The change, reverted: a full run on several threads with a dictionary of 1 M
terms or more drops its hash slots and rebuilds them, in id order with no
other allocation, at the next lookup by text or change (`fb500d8`, reverted
by `38df2c3`; the code is kept on `exp/e09-dict-drop`). The maintainer had
accepted the first change's wait. It was evaluated on top of iteration 8
(`b654de6`), the version kept before it. The decision is iteration 9's row in
`docs/specs/experiments.md`.

Raw results are in [`data/2026-11-07-e09/`](data/2026-11-07-e09/).

## Correctness

Every suite passed on the tree with the change (`fb500d8`): the core library
(two new tests: the slots drop and rebuild alike, and only on several
threads) and its doc tests; the CLI; the oracle library and `minimal`,

## Why it was reverted

On top of iteration 8 the all-cores median peak fell by 7.5 MB, with the
middle halves apart: a real gain, but under the loop's 10 MB bar, the rule
that also reverted iteration 6. Alone, against the version before iteration
8, the implementer measured 45 MB (582.8 to 537.7 MB). The two changes
overlap: both free memory that the parallel steps then reuse, and once
iteration 8 frees the base's share, the dictionary's slots add little. For
7.5 MB the change would cost a wait of about 28 ms at the first change after
a large parallel run, a rebuild path in the dictionary, and the condition on
the thread count.

The implementer's two revisions are worth keeping as lessons: the first
rebuild allocated 69 MB of temporaries, so a full run followed by one change
peaked above the version before (603 to 610 MB against 583); a rebuild in id
order fixed that. And on one thread the drop saved nothing, since nothing
there reuses the freed slots, so the drop was limited to several threads.
