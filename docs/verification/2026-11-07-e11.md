# Verification: loop iteration 11, one split per property rule, not built (2026-11-07)

The candidate: in the property family's large rounds, run each rule as one
split over all its axioms instead of one split per axiom, on the reading that
round 1's property family gains nothing on all cores because its splits are
many and small. Its stop condition was to count the splits first. The count
refuted the reading, so nothing was built. The kept version is `b654de6`
(iteration 8). The decision is iteration 11's row in
`docs/specs/experiments.md`.

Raw data is in [`data/2026-11-07-e11/`](data/2026-11-07-e11/): the temporary
instrumentation (`instrumentation.diff`, not landed), the traces of three runs
per thread mode on lubm-50, the load averages, and the script that summed them.

## The counts (lubm-50, exact and identical in every run)

- Round 1 has 24 non-empty property splits, not about 50: prp-dom 10, prp-rng
  8, prp-spo1 5, prp-inv1 1, holding 4,539,449 pairs in 604 chunks. All but
  one 998-pair split already run in 4 to 48 chunks of at least 4,096 pairs.
- On one thread the 24 splits take 8.27 ms in all, the family's whole time.

## Where round 1's property time goes on all cores

| | One thread | All cores |
|---|---:|---:|
| Family wall time | 8.5 to 8.7 ms | 8.1 to 8.2 ms |
| CPU writing the derived pairs | about 8.3 ms | 15.3 to 16.6 ms |
| CPU sorting each chunk's output (`Pending::compact`) | 0 (left to the step) | 18.1 to 19.0 ms |

- The work grows about fourfold on all cores, to about 34 ms of CPU.
- The datatype family does the same in round 1: 45 to 50 ms of CPU against 22
  on one thread.
- Round 1 holds about 80 to 85 ms of chunk CPU in 11 to 14 ms of wall time, on
  12 cores of which 6 are Efficiency cores: the pool is nearly saturated.
- Fewer forks and joins could recover at most 1.2 to 1.75 ms, the time the
  waiting thread returns after its last chunk ends.

So the limit is CPU on a busy pool, not dispatch. Fusing the splits keeps both
costs, and the estimate of 3 to 4 ms does not hold. A family's time on all
cores also includes other families' chunks that its waiting thread ran, which
the profile's reading must allow for.
